# Deploying the API

The mobile app's web build is on Netlify. Netlify serves static files, so the
API needs its own host and its own database.

**The API must be served over HTTPS.** The Netlify site is HTTPS, and a browser
refuses to call an HTTP endpoint from an HTTPS page — it blocks the request as
mixed content before it leaves the machine. The failure looks like the API being
down, with nothing in the API's logs, because nothing ever arrives. Every
platform below terminates TLS for you, so this is free as long as you do not
try to point at a bare IP.

Two pieces:

| | What | Free tier |
|---|---|---|
| Database | **Neon** — managed PostgreSQL | 0.5 GB, no expiry |
| API | **Render** — Docker web service | 750 h/month, sleeps when idle |

Render also offers Postgres, but its free database is **deleted after 30 days**,
which is a bad surprise for a project that has to still work when it is marked.
Neon's free tier does not expire.

---

## 1. Database — Neon

1. Sign up at **https://neon.tech** and create a project (pick the region
   closest to you; Frankfurt is the nearest to Baku).
2. Copy the connection string. It looks like:

```
postgresql://user:pass@ep-something-123456.eu-central-1.aws.neon.tech/neondb?sslmode=require
```

Keep `?sslmode=require` — Neon refuses plaintext connections and Prisma will
fail without it.

### Load the schema and the data

Run these from your machine, pointed at the remote database. The seed
**truncates every table**, so it is deliberately not part of the deploy — it
must never fire automatically on a redeploy.

```bash
DATABASE_URL="postgresql://…?sslmode=require" npx prisma migrate deploy
```

```bash
DATABASE_URL="postgresql://…?sslmode=require" npm run seed
```

On Windows PowerShell, set it first instead:

```powershell
$env:DATABASE_URL="postgresql://…?sslmode=require"; npx prisma migrate deploy; npm run seed
```

That loads the 1000-book catalogue and the demo accounts. It takes a minute or
two against a remote database — most of it is the books.

## 2. API — Render

1. Sign up at **https://render.com** and connect the GitHub account.
2. **New → Web Service**, pick `holbertonfinalproject-backend`.
3. Render reads `render.yaml` and fills in the runtime, the Dockerfile and the
   health check. Two variables it cannot guess:

| Variable | Value |
|---|---|
| `DATABASE_URL` | the Neon string from step 1 |
| `CORS_ORIGINS` | your Netlify URL, e.g. `https://kitabdostu.netlify.app` |

`JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are generated by Render and kept.
Do not rotate them casually — changing them invalidates every session.

Everything else has a default. No integration keys are required: each one runs
as a stub, and card payments refuse rather than silently approving.

Deploy. The first build takes a few minutes; migrations run at container start,
so the schema is in step with the code by the time it answers.

Check it:

```bash
curl https://your-service.onrender.com/health
```

> **The free tier sleeps.** After 15 minutes with no traffic Render stops the
> container, and the next request waits ~50 seconds for a cold start. Fine for
> a demo — but open the site a minute before showing it to anyone, or the first
> screen will look broken.

## 3. Point the app at it

`EXPO_PUBLIC_*` variables are inlined **at build time**, not read at runtime, so
this has to be set on Netlify and the site rebuilt. Setting it locally does
nothing for the deployed site.

In **Netlify → Site configuration → Environment variables**, add:

| Key | Value |
|---|---|
| `EXPO_PUBLIC_API_BASE_URL` | `https://your-service.onrender.com/api/v1` |
| `EXPO_PUBLIC_DEFAULT_LOCALE` | `az` |

Note the `/api/v1` — the host alone is not enough.

Then **Deploys → Trigger deploy → Clear cache and deploy site**. A plain redeploy
may reuse the cached bundle, which still has the old value baked in.

### Check it worked

Open the site, then the browser console. If the API base is wrong you will see
requests going to the wrong host, or a CORS message naming the origin that was
refused — add exactly that origin to `CORS_ORIGINS` and redeploy the API.

Signing in with `leyla@kitabdostu.az` / `password123` is the fastest end-to-end
check: it exercises the database, the API and CORS in one request.

---

## Also update `CORS_ORIGINS` for previews

Netlify gives every deploy preview its own subdomain
(`deploy-preview-3--yoursite.netlify.app`). Those origins are not covered by the
production entry, so previews will fail CORS unless you add them. For a student
project it is simpler to test on the production URL than to enumerate them.

---

## Other platforms

The `Dockerfile` is platform-neutral; `render.yaml` is the only Render-specific
file. The same image runs on Railway, Fly.io, Koyeb or a VPS. Whatever you pick
needs to:

- inject `PORT` (the server reads it; it does not hardcode 4000),
- give the container `DATABASE_URL`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`
  and `CORS_ORIGINS`,
- and terminate TLS.

---

## A note on the demo accounts

The seed creates `leyla@`, `publisher@` and `admin@` with a shared, published
password. That is fine for a graded project and wrong for anything real. If this
ever carries actual users, change those passwords — or seed without them — before
it does.
